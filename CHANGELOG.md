# dnshived Changelog

## 0.9.8.6 — released

**Upgrade instructions (from 0.9.8.5):**

1. Back up `/etc/dnshived` and `/var/lib/dnshived` on every node, and `/var/lib/dnshived-probe` on each probe host.
2. Upgrade every node, including probe hosts, in one window. Do not upgrade one node at a time: a node on this release does not accept the unsigned pings and beacons of 0.9.8.5, and is isolated until the others follow. On Debian and Ubuntu install the new `.deb` with `apt-get install ./dnshived_<version>_<arch>.deb`; on RHEL-family systems use `rpm -Uvh dnshived-<version>.rpm`.
3. Wait until every node is `STABLE` (`journalctl -u dnshived | grep FSM:TRANSITION`) and the Overview in the web UI shows no unreachable node.
4. Probe hosts log their TLS certificate fingerprint at start (`journalctl -u dnshived-probe | grep 'TLS API'`). Pin it on the Probes page if you want the HTTPS path; unpinned probes keep working over plain HTTP.

**Changes to how commands run:**

- `dnshived-status`, `dnshived-validate`, `dnshived-preflight`, `dnshived-dnsrelay-render`, `dnshived-dhcp-probe`, `dnshived-relay --status`, `dnshived --version/--check-config/--emergency-close-gates` and `dnshived-web -reset-user` may run as root.
- The daemons and the DNS relay refuse root and must run as their service account; the unit files already do this.
- `dnshived-top` must not run as root.
- Unknown flags and stray arguments print one line and the usage and exit 2; `-h` lists the flags.

**Rollback:** install the 0.9.8.5 package on every node in one window (`apt-get install --allow-downgrades ./dnshived_0.9.8.5_<arch>.deb`, or `rpm -Uvh --oldpackage`), then restore the backups if the configuration was changed on this release. The 0.9.8.5 downgrade was exercised on the testlab.

- DHCP relay counts dropped packets per client VLAN, one counter per reason (gate closed, rate limited, malformed, and so on), and `dnshived-relay --status` prints them from the running relay. A full client table and a failed downstream write, which were not counted before, now are.
- The DHCP relay runs as its own system user and group, `dnshived-relay`, instead of `dnshived`, so a compromised relay cannot reach the privileged helper's socket. The daemon user joins the group to reach the relay's gate socket. The packages create both accounts, keep `relay.json` in the relay's group across upgrades, and restart a running relay. The unit also gains ProtectHome, ProtectKernelTunables, ProtectControlGroups, RestrictRealtime and LockPersonality. **Upgrade note:** upgrading restarts the DHCP relay on each node, which briefly interrupts DHCP relaying there.
- The relay's runtime directory `/run/dnshived-relay` is created by tmpfiles instead of the unit's `RuntimeDirectory=`, and an upgrade removes the old track files before the relay restarts. On SELinux-enforcing RHEL, the relay no longer fails to start after an upgrade with the old track files still present (systemd could not re-own them).

- Web UI search dropdowns (VLAN ID, VRRP ID and every other find-as-you-type list) showed only the first 200 entries with no sign that more existed, so the scope wizard's VLAN list ended at 201 and its VRRP list near 200. The list now ends with a "N more — type to narrow" row. Clicking into the field selects its text, so typing replaces the current value instead of appending to it, and an exact match is listed first, then values starting with the typed text, so Enter picks what was typed.
- `log_level` now takes effect; before, every level logged everything. `warning` logs errors, failures, denials and security refusals; `info` adds state changes (scope gained or lost, VRRP state, DHCP gate, failover, config commits, nodes joining or leaving, user changes); `debug` adds every routine repeating success (witness renewals, peer pings, probe results). `auto`, the default, logs like `info`, switches a subsystem (the part of a log tag before the colon, e.g. `AGENT` in `[AGENT:TOKEN_DENY]`) to `debug` detail for 5 minutes after a warning in it, and replaces the suppressed routine messages with one summary line every 10 minutes. Witness renewals no longer log a line every 5 seconds per scope. A level change applies without a restart. **Upgrade note:** a cluster set to `info` or `warning` now really logs less than before.
- Core nodes check every witness grant and renewal before counting it as an arbiter's vote: the PSK signature must be valid, the token must name this scope, this node and its current incarnation, and its expiry must be in the future and at most a minute ahead. Before, any `accepted` answer counted, so in a cluster without TLS a forged response could make a core serve a scope it did not hold. A rejected answer is logged with the arbiter's address and the reason. Arbiters have signed their grants since 0.5.2, so cores keep working with older arbiters during a rolling upgrade.
- DHCP relay: fuzz tests for the request and reply paths (malformed packets must never crash the relay or be forwarded with a wrong relay address) and benchmarks for per-packet cost, as the baseline for the relay hardening that follows.
- A scope could end up served by no node after its owner restarted: when a core that was serving a scope other than its preferred one restarted, it computed the preferred core as owner, while the other cores kept the restarted core as owner from their own last answer. With the same generation on all nodes, nothing noticed the difference and the scope stayed unserved until another restart or rebalance. A core now keeps a remembered owner only while that owner is seen serving the scope; once it has been seen not serving for 30 seconds, every core recomputes the owner the same way and they agree again. In a rolling upgrade, cores that are not yet upgraded behave as before.
- Upgrades restart a DHCP relay or DNS relay that still runs the old binary: when the daemon asks for a relay reload and the running process's binary has been replaced on disk, the helper restarts the relay instead and logs it. Before, an RPM upgrade only reloaded `dnshived-relay`, so it kept running the previous version until the next manual restart.
- A core rejoining the cluster takes over its peers' fencing watermark before it computes its first desired-state map, so that map carries the cluster's current generation instead of the node's older stored one.
- Cores compare their desired-state maps: each core announces a hash of its map (and the map itself for up to 512 scopes) in the peer handshake, and two cores with the same generation but different maps for more than 45 seconds (longer than the 30-second grace that heals the split after an owner restarts) log a `[DESIRED:SPLIT]` warning with the scopes they disagree on, every 5 minutes while it lasts and once when it ends; a shorter split of 5 seconds or more is logged with its length when it heals. Peers on older versions do not announce a map and are skipped.
- Faster recovery after a core that served a scope other than its preferred one restarts: when a peer's desired-state map disagrees at the same generation and this core's remembered owner is not serving the scope, the remembered owner is dropped right away instead of after the 30-second grace, so the cores agree on the next pass.
- `make rpm` packs new files that are not yet committed; before, the source tarball came from `git stash create`, which leaves untracked files out, so a build from a working tree with a new source file failed.
- A gap of 5 seconds or more in which no node served a scope is logged when a node serves it again (`[AGENT:UNSERVED] ... was served by no node for ...`), also below the 30-second warning, so every handover leaves its length in the log.
- DHCP relay limits, on by default: in-flight requests per VLAN are capped (`pending_per_vlan`, default 2048) and expire after 30 seconds instead of 120, so one flooding VLAN can no longer fill the relay's table for every other VLAN; each client MAC is limited per VLAN (`client_rate_limit`/`client_rate_burst`, default 10/s with a burst of 20) on top of the per-VLAN limit. A request dropped by any limit is counted and logged as a warning (at most once per 30 seconds per VLAN and limit). The new fields are optional in `relay.json`, kept when the file is re-rendered, and `-1` turns a limit off. The 1-minute relay metrics line gains `client_limited=` and `pending_full=` at its end. **Upgrade note:** a client sending more than 10 DHCP requests per second on one VLAN, or a VLAN with more than 2048 unanswered requests at once, now has requests dropped.
- Diagnosability: a scope that no node serves for more than 30 seconds is logged on every core as a warning (`[AGENT:UNSERVED]`) with that node's reason, the owner its desired-state map names and the generation, repeated every 5 minutes while it lasts, and once more when a node serves it again. Every change of a scope's owner in a node's desired-state map is logged (`[DESIRED:OWNER]`). Before, a scope that no node served produced no log line at all.
- Audit follow-ups: a `[DESIRED:SPLIT]` line lists at most 20 disagreeing scopes and then says how many more there are, instead of up to 512 scopes per line. The DHCP relay's per-client table holds at most 1024 MACs per VLAN and 16384 across all VLANs (before, 4096 per VLAN), and a flood of new MACs can trigger at most one idle-entry sweep per second. `make rpm` adds new files only under the source directories, not from the whole working tree.
- DHCP relay hardening. A reload that changed the DHCP server address could race with requests being forwarded at that moment; the server socket is now swapped atomically. An interface added in the same reload as a change of the cluster-wide `rate_limit`/`rate_burst` got the old values until the next reload; it now gets the new ones. Requests dropped by the rate limit cost less than forwarded ones (no log formatting while the warning is throttled), the clock is read once per request instead of twice, and replies are relayed without per-packet allocations in the common broadcast case. No configuration or behaviour change.
- The privileged helper's socket is hardened: each connection has a 60-second deadline and a 64 KiB request limit, at most 64 connections are served at once, and shutdown waits at most 45 seconds for requests in flight. Denied requests and the restart-helper and finish-decommission commands log the caller's uid and pid. The socket is created 0660 from the start, and a stale socket is removed only if it really is a socket; anything else at that path stops the helper with an error. Access is still decided by the socket's group, as before.
- Starting the daemon twice is refused: a second `dnshived` on the same node exits with an error naming the running process, before it binds any port or changes any service. Unknown command-line arguments now print the usage and exit with status 2; before, they were ignored and the daemon started. `--check-config`, `--emergency-close-gates` and `--version` are unchanged.
- The log line that reports a reload's effect on keepalived now reads `[AGENT:VRRP_PRIORITY] keepalived reloaded <N>ms after decision`, and the serving-set change line is `[AGENT:SERVING_SET]` (was `[BENCH:DECISION]`). Log text only; no behaviour change. Anything that greps for the old tags needs the new ones.
- The Makefile's `deploy` and `deploy-all` targets and their `VM_IPS`, `SSH_USER` and `SSH_OPTS` variables are removed. They copied bare binaries instead of installing a package and checked the result over plain HTTP against the HTTPS API, so they always reported the nodes as unreachable. Install the `.deb` or `.rpm` instead.
- Joining a core or adopting a probe no longer sends the cluster's secrets in cleartext. The push to a node in bootstrap mode (cluster config with the PSK and API tokens, web users, the web and cluster TLS keys, or the probe's config with its tokens) went over plain HTTP together with the join code, so anyone able to read the management network at that moment got all of it. The push is now encrypted and authenticated with a key derived from the join code (AES-256-GCM), and the join code itself is no longer sent. In bootstrap mode, the setup pages on port 80 now redirect to the HTTPS listener (port 443, self-signed), so join codes typed into the wizard are not sent in cleartext either; the machine API under `/api/` stays on port 80. If port 443 cannot be opened, the pages stay on plain HTTP as before. A node in bootstrap mode still accepts the old unencrypted push from an older sender and logs a warning that the secrets crossed the network in cleartext. **Upgrade note:** a node in bootstrap mode must run this version or later to be joined or adopted by it; an older one answers "wrong join code", and the error says to upgrade it first.
- The probe host verifies the cores it talks to. Before, it accepted any certificate, so a machine posing as a core could collect the probe's cluster token. Adopting a probe now also hands it the cores' certificate (the public part only, as `cluster_cert_pem` in `probe.json`), and the probe accepts only that certificate. A probe adopted by an older version has no `cluster_cert_pem` and connects as before, with a warning; adopt it again to get the check.
- "No cluster certificate configured — connections to cluster peers are not verified" is now logged as a warning, so it also shows at `log_level` `warning` and `auto`. Before, it was an info line and was hidden there.
- `dnshived-top` can verify the nodes against the cluster certificate: `-tls-cert <file>` (or `tls_cert=` in `~/.dnshived/rc`) with a copy of `/etc/dnshived/tls/cert.pem` from a core switches to HTTPS and accepts only that certificate, instead of `-tls-skip-verify`, which accepts any. The README quick start uses it.
- CI runs the tests: `go test ./...` (as root with a `dnshived` service user, as on a real install), the race detector on the coordination and safety packages, and a build of every binary including the DNS relay module, which it did not build before. Before, CI only built and vetted.
- The quorum calculation has its own tests, including every possible split of the three cores: two nodes that cannot see each other never both hold quorum.
- README: the safety promise now names the conditions it rests on and the clock assumption, instead of calling the failure mode structurally impossible.
- An arbiter that restarts grants no new witness tokens for 15 seconds (one token lifetime). Grants were written to disk up to 2 seconds after they were answered, so an arbiter that crashed right after a grant could forget it and grant the same scope to a second core while the first core's token was still valid. During the pause, renewals keep working and the arbiter re-learns any grant it lost from the holder's signed renewal; anything it does not re-learn has expired by the end of the pause. A request refused this way is answered as a normal denial with the remaining time. A restarted core still gets its tokens from the other two arbiters.
- A corrupt or unreadable `incarnation` file no longer resets the node's incarnation to 1, which could repeat a value the node had already used. The node now takes the current Unix time as its incarnation, which is higher than any value the counter reached before, and logs a warning naming the file.
- A daemon started as root on a node that has the `dnshived` service user is refused with an error naming that user; before, a root run rewrote the dnsmasq and keepalived configuration files as `root:root`, and dnsmasq, which runs as `dnshived`, failed with "Permission denied" until the real daemon rewrote them. Configuration files written while running as root are now owned by `dnshived:dnshived`, and a leftover temporary file from an earlier run no longer blocks the next write. `--version`, `--check-config` and `--emergency-close-gates` still work as root; bootstrap mode is unchanged. **Upgrade note:** a custom unit that runs the daemon as root no longer starts; the shipped unit has always used `User=dnshived`.
- The web UI's Basic-auth verify cache is keyed by HMAC-SHA256 under a random secret that exists only in the process, instead of an unkeyed SHA-256 of the username and password. A memory dump of the web UI no longer gives an offline guessing target for passwords. The cache is in memory only, so nothing changes on disk and a restart just empties it.
- A daemon start no longer knocks the scope VIP off the node. The daemon now sends the VIP with each interface request, and the helper removes only addresses that match neither the node IP nor the VIP. Before, every start deleted keepalived's VIP, and it came back about 0.6 s later, so the holder flapped MASTER → BACKUP → MASTER. An older helper with a newer daemon behaves as before.
- A probe host can be adopted again after a core node self-decommissions. Adopting a node as a core stops its probe units so the two roles never run together; a self-decommission now starts them again before the node returns to bootstrap mode.
- A self-decommission removes the empty `inet dnshived` nftables table that older versions left behind.
- When no scope is eligible for the relay, `relay.json` no longer keeps the client interfaces of removed or disabled scopes: the file is emptied (rate limits kept) before the relay is stopped.
- A scope can be moved to another VLAN ID or trunk interface from its page. Only the parent and VLAN ID change; the VIP, node IPs and DHCP pool stay as they are. The move is staged like any other edit, and a VLAN already in use on that trunk is refused.
- Probe hosts serve their API over HTTPS on port 9445 with their own self-signed certificate, separate from the cluster's. Its SHA-256 fingerprint is logged at start and shown on the Probes page. The web UI and `dnshived-top` (`-probe-pin host:port=sha256:…`) can pin that fingerprint, and a pinned probe is then reached only over HTTPS with that certificate. The web UI checks the probe over TLS before it saves a pin. The plain API on port 9444 stays until every probe is upgraded; probes not yet pinned keep working over plain HTTP and are shown as such. A probe's certificate is regenerated after a self-decommission, so its pin must be set again.
- `dnshived-validate` reaches pinned probes over HTTPS too (`-probe-pin host:port=sha256:…`, or the pins in `web.json`), and the Probes page can remove a pin (Unpin), which returns that probe to plain HTTP until it is pinned again.
- A failed relay close no longer releases the scope's arbiter token. The token is kept and renewed until the relay confirms the close, and the close is retried each tick (`[AGENT:CLOSE_PENDING]`, then `[AGENT:CLOSE_RESOLVED]`). Before, a refused close cleared the token, so another core could open the scope while this relay still forwarded DHCP for it.
- An open whose answer from the relay was lost is closed on the relay before its token is dropped, so the relay cannot keep forwarding without a token.
- The probe helper's trunk-parent allowlist no longer accepts VLAN-style names or the interface that carries the default route, and its interface reconcile no longer removes IPv6 (link-local included) addresses.
- **Upgrade note:** upgrade all cluster nodes in one window. A node running this release does not accept the unsigned pings and topology beacons of 0.9.8.5 (they are refused as `DENY_UNSIGNED`), so during a rolling upgrade the upgraded node is isolated from the others until they are upgraded too.
- An upgrade from 0.9.8.5 removes the nftables DHCP rules that release left behind. The removal ran before the helper was connected, so it failed silently and the rules kept dropping DHCP on the nodes that owned a scope. It now runs after the helper is connected.
- Files the daemon and helpers write for dnshived (`dnsmasq` host files, the DNS relay and probe configs, the web users file) are owned by `dnshived:dnshived` even when root writes them.
- Every binary checks its command line: an unknown flag or a stray argument prints one line and the usage, and exits 2; `-h` lists the flags.
- Every binary checks the user it runs as. The daemons (`dnshived`, `dnshived-relay`, the DNS relay, the probe and the web UI) refuse root and need their service account, and a missing account is an error. The root helpers need root. The tools that can need root (`dnshived-status`, `dnshived-validate`, `dnshived-preflight`, `dnshived-dnsrelay-render`, `dnshived-dhcp-probe`, and the root-capable modes of `dnshived --version/--check-config/--emergency-close-gates`, `dnshived-relay --status` and `dnshived-web -reset-user`) may run as root. `dnshived-top` refuses root.
- A second copy of a daemon or helper refuses to start and names the running process. Each keeps a lock file, and a socket path is replaced only when nothing answers on it; a socket that still accepts connections is refused.

## 0.9.8.5 — released
Web UI user management and interface-detection release. Login form with sessions, three roles (admin, scopeadmin, readonly), users replicated to every core, password reset by email with SMTP settings; the pre-onboarding interface check now detects trunks and management interfaces (rp_filter on address-less trunks, and onboarding always talks to the core daemon); core nodes pin the cluster certificate; `dnshived-validate`'s dual-active check works. Verified on a freshly built cluster (3 cores incl. CentOS Stream 9, 1 probe host): founding, onboarding, users and mail, self-decommission and re-onboarding of the CentOS core with its interface names detected.

**Upgrade notes:**
- Core nodes now verify each other's certificate: every core must serve the same cluster certificate, as founding and onboarding set it up. A hand-built cluster with per-node certificates must switch to one shared certificate first.
- The web UI asks for a login once after the upgrade (form instead of the browser popup). On first start the cores merge their users files into one replicated users document; HTTP Basic credentials from scripts are still accepted.
- An existing cluster keeps resolving interface names at runtime; per-node interface names are stored the next time a node is replaced or re-onboarded.

Known issues: after a self-decommission the probe daemon stays disabled, so the host cannot be adopted as a probe host until `dnshived-probe` is started by hand, and an empty `inet dnshived` nftables table is left behind (harmless). Probe hosts keep reverse-path filtering on their trunks, which drops the cores' topology beacons there (no effect today). Not yet tested live: cluster certificate rotation and a failover with certificate pinning on; storing management names from the founding wizard (covered by tests; onboarding is verified).

- The pre-onboarding interface match detects trunks again. The candidate's probe leaves an address-less trunk with its management address as source, and on the listening node's address-less trunk the kernel's reverse-path filter (rp_filter=2, the Debian 13 default) dropped it. The helper's `link-up` now sets rp_filter=0 on an interface that carries no IPv4 address (never on the management interface or any addressed one), as scope creation already did; this also covers topology beacons on a cluster without scopes.
- Founding wizard stores each node's own management interface name (the interface the founder reaches it on) as a per-node override and shows it in the node list and review; before, every node got the founder's name, which only worked through altname resolution.
- Diagnosability: a failed interface-probe send is logged, and a trunk that heard nothing logs its rp_filter value.
- `dnshived-validate`'s DHCP dual-active check works: it asked the core nodes for probe results, which only probe hosts serve, so it never fired. It now queries the probe hosts (`-probe-addr`, or `probe_hosts` from `/etc/dnshived/web.json`) and says at startup when no probe host is known.
- The DHCP relay and DNS relay are no longer shown as inactive/dead when every scope is disabled: only enabled scopes count, and relay interfaces of disabled or removed scopes are no longer listed.
- Overview shows per trunk whether it is verified (a beacon from another core was heard on it) or only assumed. Every configured trunk is now beaconed, not only trunks that carry a scope, so a cluster without scopes is checked too.
- Core nodes verify each other's TLS certificate against the cluster certificate (as the web UI already does) instead of skipping verification. A refused peer is logged with its certificate fingerprint. **Upgrade note:** every core must serve the same cluster certificate, as founding and onboarding set it up; a hand-built cluster with per-node certificates must share one first.
- Web UI user management. Login is a form with a signed session cookie instead of the browser's password popup (logout works; the session survives a mgmt-VIP failover; 30 min idle, 12 h maximum). Admins create, edit, disable and delete users on the new Users page; roles are admin, scopeadmin (everything served to clients: scopes, DHCP/DNS settings, templates, local domains) and readonly. A scopeadmin can commit only when every staged change is within its rights. The last active admin cannot be deleted, disabled or demoted, and nobody can demote, disable or delete themselves. Every user change is written to the audit log.
- Users are replicated to every core: a change on one web instance reaches the others at once, and every instance checks the others once a minute, so a core that was down or newly added catches up by itself. The first replication merges each core's existing users instead of overwriting them. `dnshived-web -reset-user` (now also `-role scopeadmin` and `-email`) spreads the same way and no longer needs a restart.
- Password reset by email ("forgot password?" on the login page): single-use link, valid 30 minutes, the same answer whether or not the user exists, rate-limited. Users get a notification email when their password, role or status changes.
- Mail settings (Cluster config → Mail): SMTP server, port, STARTTLS/TLS/none, login, sender, optional custom CA, and the public URL used in reset links. "Test settings" checks connection, TLS and login without sending; "Send test email" sends one.
- Onboarding a core from the Discovered list could talk to the wrong daemon: a host waiting for adoption runs both the core daemon (port 80) and the probe daemon (port 9444), and the list kept whichever announced last. The interface check then got no interface bursts and no management interface, so no per-node interface names were stored. The interface check and Inspect now always contact the core daemon (port 80), as the adopt push already did, whatever port the list showed; a candidate that reports no management interface is logged.
- `make rpm` removes older dnshived RPMs from `rpmbuild/RPMS` first, so the documented `dnf install` glob installs exactly one build; the spec builds without `systemd-rpm-macros` (tmpfiles directory fallback).

## 0.9.8.4 — released
Hardening and fresh-install release. dnshived runs unprivileged, with root left only in the helpers and keepalived; RHEL/CentOS (SELinux) install and upgrade paths fixed; web UI security hardening and performance; founding wizard stores node addresses with their port, so a freshly founded cluster no longer comes up partitioned. Verified on a fresh founding (3 cores incl. CentOS Stream 9, 1 probe host, 1 scope).

Known issue: the pre-onboarding interface match still detects no trunk (all trunks show "not detected" and need "add anyway"); the cluster runs normally because each node resolves its trunk names at runtime, but no per-node interface names are stored. Being reworked into a beacon-based interface assignment.

**Upgrade note: dnshived.service no longer runs as root.** The upgrade restarts dnshived once per node (as every upgrade does) and moves ownership of /etc/dnshived and /var/lib/dnshived to dnshived:dnshived.

- Web UI security: the cluster PSK and API tokens are never sent to the browser any more (readonly users could read them, including admin tokens); fields are write-only ("leave blank to keep"). Form posts from other sites are refused (Origin/Sec-Fetch-Site check against cross-site request forgery). Failed logins are rate-limited per client address and per user, and password checks run at most two at a time. The HTTPS server has timeouts and request size limits, and every response carries security headers (no framing, nosniff, HSTS, referrer policy). Connections from the web UI to the cores and to sibling web instances verify the cluster certificate instead of skipping verification.
- Saving the cluster config in the web UI kept the per-node trunk names but dropped the per-node management interface names (added in this release).
- Founding wizard: node addresses are stored with their port (core API port for cores, 9444 for probe hosts). Typed without a port, every peer was contacted on port 443 and the new cluster came up with core-1 isolated and the probe host shown down.
- The interface match brings the listening node's trunk NICs up first. On a node in bootstrap mode, or a cluster without scopes yet, the trunks were down, so founding stored no per-node interface names and an onboard/replace would have been refused for an undetected trunk.
- Founding wizard shows the detected interface per trunk for every node and refuses a node with an undetected trunk unless "add anyway" is ticked (it used to drop that silently).
- Overview names the real reason when a node answers with something other than JSON (e.g. "HTTP 301 Moved Permanently, not JSON") instead of a raw decoder error.
- Web UI login takes the same time for unknown and known user names (an unknown name was rejected at once, a known one after the ~0.65 s password check, revealing which names exist).
- The "+ insert into this template" button for local domains works: its JavaScript argument ended the HTML attribute early (and let record text spill into the button's attributes).
- Web UI performance: a successful login stays valid without re-hashing the password until the users file changes (it re-checked PBKDF2 every 30 s, ~0.65 s per click after a pause); responses are gzip-compressed; while someone is using the UI, the cluster snapshot behind Overview is refreshed in the background, so a page never waits for the cores.
- Performance: the agent reads unit states from one shared `systemctl show` snapshot per tick instead of one process per unit and check; `/api/v1/daemons` caches version strings per binary until the binary changes; the time check reads the kernel clock state (adjtimex) instead of running timedatectl and chronyc, which also ends the chronyc SELinux denials on RHEL. Measured on a lab core before: ~107 process starts and 4.2 s CPU per minute.
- dnshived runs as user dnshived with NoNewPrivileges and one capability, CAP_NET_BIND_SERVICE, for bootstrap mode's setup wizard on ports 80/443. Root is left only in dnshived-helper and keepalived.
- Everything dnshived still did as root goes through the helper: bringing a beacon interface up (`link-up`), removing orphan DHCP gate rules (the orphan sweep called nftables directly even with a helper), enabling/stopping the web UI, helper and probe units at adopt, stopping units and clearing the helper's state at self-decommission, and scheduling the restart into bootstrap mode. A failed `link-up` is logged instead of ignored.
- The emergency gate close on stop (ExecStopPost) runs with full privileges, so its direct nftables fallback keeps working.
- Direct mode (no helper socket) is gone; the helper is always used. The daemon unit no longer needs write access to /proc/sys.
- keepalived (scope and mgmt units) keeps root but only the capabilities it uses, plus NoNewPrivileges. dnshived-helper gets NoNewPrivileges; limiting its capabilities waits for an RHEL test (restorecon).
- dnsmasq runs as dnshived from the start (never root), with only CAP_NET_BIND_SERVICE, CAP_NET_ADMIN and CAP_NET_RAW; its lease script runs as dnshived too. Under SELinux, root inside dnsmasq_t has no dac_override and could not read the dnshived-owned configs.
- /run/dnshived is group-writable for dnshived with the sticky bit, so the daemon can create its lease socket but cannot replace keepalived's PID files.
- dnshived-web-helper and dnshived-probe-helper no longer reset /run/dnshived to 755 on start (that undid the sticky group-writable mode, so dnshived could not recreate its lease socket after a web-helper start).
- dnshived-relay and dnshived-probe drop CAP_NET_RAW: binding a socket to an interface needs no capability since Linux 5.7, and every supported OS has 5.14 or newer.
- dnshived-web-helper keeps root but no capabilities at all (its only command is restarting dnshived-web), plus NoNewPrivileges and a read-only system.
- keepalived and dnsmasq units no longer set NoNewPrivileges: under SELinux it blocks their transition into keepalived_t/dnsmasq_t, so keepalived could not open VRRP sockets and dnsmasq did not start (found on CentOS Stream 9). Their capability limits stay.
- The pre-onboarding interface match never detected any trunk on a running cluster: its listener used UDP 9446, which the topology beacons already hold on every trunk, and the bind error was swallowed. Interface probes now use UDP 9448, and a failed listen is logged.
- Replace/onboard is refused (HTTP 409, nothing changed) when the interface check hears no candidate interface on a trunk; the web UI's Pending changes page offers an explicit "onboard anyway" checkbox for the commit.
- RPM binaries report the same version string as the .deb (VERSION-N+HASH); the different format made the pre-onboarding check report a version mismatch between identical builds.
- Onboard and replace store the node's real interface names: the pre-onboarding interface match (the candidate's broadcast bursts heard on the cluster's trunks) is saved per node, as founding already did; a replace drops the old node's entries. The management interface gets a per-node name too, taken from the interface the cluster reaches the candidate on.
- relay.json was written with the cluster's interface names even on a node whose names differ (the change check used the resolved names), so the relay could bind the wrong interfaces.
- RPM/SELinux: the lease file and dnsmasq log in /var/lib/dnshived get dnsmasq_lease_t/dnsmasq_var_log_t; dnsmasq_t could not write them (var_lib_t), so central DHCP could not start on RHEL-family.
- A scope VLAN that already exists under another name (same VLAN ID on the same NIC, e.g. ens19.110 after the node's names resolve to eth1) is removed and recreated under the right name instead of failing with "VLAN device already exists".
- Every node resolves configured interface names to the kernel name (a kernel altname such as ens19 on a host booted with net.ifnames=0 now maps to eth1) before using them for keepalived, beacons, rp_filter and sockets; before, `ip` accepted the altname while the rest failed.
- Self-decommission and the orphan sweep could not delete VLAN interfaces on a node whose interface names differ from the cluster's: they passed the cluster's trunk name to the helper, which then deleted a non-existent ens19.110 instead of eth1.110 and reported success.
- Self-decommission empties /var/lib/dnshived instead of failing to delete the directory itself (the non-root daemon may not remove it), and no longer asks the helper to stop the dnsmasq@ template unit.
- RPM upgrade restarts only running units: it never restarted a running web UI (it kept serving the old binary) and started the probe pair on core nodes.
- RPM: the post-install script called /usr/bin/dnshived-preflight, but the package installs to /usr/local/bin. The script aborted there, so an RPM install never set the SELinux file contexts or enabled/started any service, while dnf still reported success.
- dnshived-probe-helper and dnshived-probe-vlans@ keep root only with the capabilities they use, plus NoNewPrivileges.

## 0.9.8.1 — released
Bugfix release for the pulled 0.9.8, from a fresh 4-VM Debian 13 install and repeated fresh-cluster runs.

**Upgrade note: dry-run is gone. A cluster that is in dry-run today starts serving real DHCP/DNS as soon as this release is installed.**

Install and packaging
- New `dnshived-preflight` runs at install time: checks required binaries and stops/masks the distro's own `dnsmasq.service`, which wildcard-binds port 53. A failed check aborts the install with a clear message. Only a wildcard bind on 53 is flagged, not dnshived's own listeners.
- `dnshived-probe` and `dnshived-probe-helper` run as the `dnshived` account (they hardcoded a non-existent `admin` user); `probe.json` is group-readable by `dnshived`.
- docs/INSTALL.md recommends `dnsmasq-base`, not `dnsmasq`.
- `dnshived-web` and `dnshived-web-helper` keep running across a package upgrade.
- Probe, probe-helper and per-scope dnsmasq units have a restart limit (10 in 5 minutes).
- One join code per fresh host, valid for either role, in `/run/dnshived-bootstrap/otp` (no longer in /tmp).
- `dnshived-web -reset-user` leaves `webui-users.json` readable by the web UI (0640, group `dnshived`).

Founding and onboarding
- A founded cluster enables privilege separation by default (`helper_socket` set); the field is no longer editable in the web UI.
- Founding derives the probe host's TLS setting from the core config, so a probe adopted at founding can fetch its configuration.
- Founding fills the probe's `trunk_parents`, and the probe helper reads them from `probe.json` live.
- New /24 scopes get suggested defaults: VIP .254, gateway .1, DHCP pool .200-.250, upstream 1.1.1.1 and 8.8.8.8. Other prefix lengths are left to the operator.
- Onboarding no longer restarts dnshived on the existing cores, keeps a configured member that is currently down, and no longer shows healthy peers as UNREACHABLE right after a start.
- A bare address without a port gets the convention port (daemon and web forms).
- An unreachable node can be force-removed from membership, behind a second confirmation.

Decommission
- A decommissioned node no longer stays "alive" on the survivors (backup-path results and trust scores cleared).
- A decommission reaches every surviving node, and re-onboarding at an old address re-adds the peer everywhere. Overview warns when nodes disagree on membership.

Network plane
- VLAN construction brings the parent trunk up first (helper, probe helper and direct mode).
- `rp_filter=0` on trunk parents (the units may write `/proc/sys/net/ipv4/conf`), so Debian 13 nodes see topology beacons on their trunks; a TRUNK PATH coherence warning names the likely cause.
- Topology beacons start on trunks added at runtime, without a restart.
- Core nodes agree on a scope's owner after a restart (observed lease holder, not own history).
- Probe coverage for untagged scopes (vlan_id 0).

DHCP and DNS
- dry-run removed: every node always serves; a legacy `dry_run` key is stripped on load (docs/FREEZE.md updated, contract break).
- Central DHCP renders option 54 (the scope VIP) and option 6 (every configured core's address) explicitly, and the relay keeps option 54 at the VIP, so renewals survive a failover.
- The probe accepts the scope VIP as a legitimate DHCP server: no false ROGUE DHCP.
- The dead per-scope `upstream` field is removed everywhere; the cluster-wide upstream stays.
- VIP, gateway, node_ip and DHCP range may not be a subnet's network or broadcast address.

Web UI
- Saving a change no longer drops the management VIP: keepalived-mgmt is reloaded only when its config changed, and a VIP change moves the address without a fresh election. `vip_host` follows the VIP live, and the Saving page finds the UI at the new VIP.
- Ports 80/443 redirect to the web UI (`CAP_NET_BIND_SERVICE` only, never root).
- The wizard no longer suggests the network address as VIP.
- Inline "probe now" button on the Probes tab.
- Cluster paths lists VLAN paths under their trunk, collapsed, with an unreachable count.
