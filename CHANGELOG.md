# dnshived Changelog

## 0.9.8.9 — unreleased

- Restoring a backup: the limit of five wrong passwords before the lock could be exceeded by one or two guesses when several attempts arrived at once, because a failed guess was counted only after the next waiting attempt had already checked the lock. The failure is now counted before the next attempt is let in.
- The theme button in the top bar has a fixed width, so the buttons beside it no longer move when the colour scheme changes.
- "Back" links go back to where you came from. The web UI now remembers the page before the current one (a second cookie next to the one that result pages already use; reloading or the automatic refresh of a page changes neither). The Daemons page, the probe detail page and the scope detail page use it for their back link (the page you came from is the one remembered before this request; on a reload it is the previous-page cookie), with their old fixed target as the fallback when there is no earlier page. Before, the Daemons page always led to the cluster settings, whichever page you had come from.
- The Security pages open on their first tab: the menu item leads to the API tokens page, which is now the first tab of the strip, followed by Users & password policy and Mail & reset.
- Overview cards with more to say: Scopes shows a bar of the served scopes, how many are not served or paused, and how many scopes each core node serves; Probes shows how many results are in, pending, stale or without a VLAN on the probe host, how many scopes have issues (and how many of them name a rogue DHCP server), and the state of the probe host; Cluster paths lists the worst trunk paths with their status and trust, and how many VLAN paths run over them.
- Tabs in the web UI. Cluster settings has the tabs Nodes, Interfaces & VIP, DNS & DHCP addresses and Misc, with one Stage button that shows only on the tabs that belong to the form. DHCP & DNS has Default DHCP options, DNS records & checks, Templates and Local domains. Maintenance has Backup, Restore, Export and Import. Logs has General, Audit and Daemon logs, and a Daemons tab that opens the daemon page. Probes has Results, Manual probes, Probe hosts & TLS, History and Behavior. Security shares one tab strip between its three pages: Users & password policy, API tokens, Mail & reset. Every old address and anchor still works: a link such as `/config#discovered` or `/probes#manual` opens the tab that holds that part. A field that is invalid inside a hidden tab opens its tab instead of silently blocking the save. Without JavaScript all parts of a page stay visible. The page title of the old "Config management" is now "Maintenance", the cluster configuration page is titled "Cluster settings", and the Mail, Users and Security pages carry the Security heading.
- DHCP & DNS: the default DHCP options, the global DNS records and the records of a local domain are shown one line per entry, each with a menu (Edit, Copy, Delete) and a filter once there are more than eight lines. The text box underneath is still what the form sends, so nothing changes for saved configurations, exports or older nodes; "Edit as text" shows it again. The existing add rows (option type with its hint, DNS record builder) keep filling the list. The template lists use the same ☰ menu as the scope list (Edit, Delete).
- Overview: a Recent events card (the newest events of all nodes, scrollable, read from the cluster snapshot that the page already fetches, so it adds no request).
- The Probes page no longer shows the "Add probe" form while a probe host is onboarded; the form comes back when none is left.
- On a phone, the user list, the existing backups, the daemon list, the cluster nodes and the template lists show each row as a small card with the column names. Other tables keep scrolling sideways.
- Web UI navigation redesigned: one row, in the order Scopes, Probes | DHCP & DNS, Security, Maintenance, Cluster settings, Logs. The dnshived logo is the link to the Overview and no longer has a second text line; each item explains itself in a tooltip instead. The page you are on is highlighted (the longest matching address wins, so the cluster settings, the scope pages and the templates each light up their own item). Below 1180 px wide the items fold into a Menu button; on a phone the buttons move to a second row and every control is at least 44 px high. The menu entries were renamed: "config management" is now Maintenance, "cluster config" is Cluster settings, and "scope options" is no longer an item of its own (it stays reachable from the Scopes page and keeps its address). The navigation now sits above the page title on every page, as in the proposal.
- The Overview is a grid of cards: Cluster nodes, Scopes, Probes, Needs attention, Cluster paths and Health checks, with Witness, node IDs and tokens in a fold-out at the bottom. Needs attention gathers unreachable nodes, daemon issues, probe issues (rogue DHCP servers stay marked) and the coherence warnings in one list and says so when there is nothing to report. The node table shows name, state, version and info; role, host name, address and system load moved into the tooltip of the name. The cards use one column on a phone, with Needs attention first.
- Web UI colours: text on filled buttons, badges and the active tab now uses its own colour per theme, and the status colours of the glowing theme were darkened. Every text and background pair of the shared layout now reaches a contrast of at least 4.5:1 in all three themes, and a test keeps it so. Before, white text on the blue buttons of the dark theme and on the green, orange and red buttons of the glowing theme was hard to read. The "pending changes" button in the top bar showed dark text on its blue background in every theme; it is white now (dark in the dark theme).
- The probe-host list of the web UI is now kept in step between the web instances by a revision, like the users. Before, adding, removing, renaming or pinning a probe host was sent to the other instances once; an instance that was down at that moment never learned of it. Now each instance compares its list with the others every minute, takes a newer one, and sends its own to one that is behind. A list that was never synchronised before is merged by address, so no probe host is lost. The old per-change sending stays as the fast path. Instances still on 0.9.8.8 keep working; they answer 404 on the new endpoints and catch up once upgraded.
- A users or probe-host document received from another instance is refused with HTTP 400 when its revision is negative or absurdly large, when a field is oversized, or (probe hosts) when the list is missing; the users document is also limited to 2,000 users and 20,000 reset tokens. A role this version does not know is accepted, so a newer version can add one.
- The cluster configuration now carries a revision (`config_revision` in `cluster.json`, shown in `/api/v1/status`), raised by one on every committed change. A node that was down during a commit and comes back with a lower revision and a different configuration gets the current configuration from the web UI within about two minutes, logged and written to the audit log as `config.catchup`. A node whose configuration differs at the same revision (for example after a hand edit) is only flagged on the Overview page, never changed. Nodes that do not report a revision yet (0.9.8.8 and older) are listed and left alone.
- **Outage rules** (they apply only when every configured core runs this version or newer; before that nothing changes, and the Overview names the nodes that block them). A configuration commit is refused with HTTP 503 (`no_quorum`) on a node that does not see a strict majority of the configured cores, so an isolated node can no longer accept a change. A commit staged on an outdated base is refused with HTTP 409 (`stale_base`) on a node that already has a newer revision. A starting node does not start scopes or raise its VRRP priority until it has compared its configuration with its peers: it waits up to 30 seconds, then serves with an "unverified config" notice if no peer answers, or stays held while a peer has a newer configuration, until the catch-up has run. A membership epoch in `cluster.json` and a console command `dnshived --force-standalone` (root, asks for confirmation) let an operator who lost two of three cores keep the last one serving; a node that comes back with an older epoch is held and reports that it was removed while away, until it is re-adopted. The web UI waits up to 30 seconds after a start for the first sync of the users before it accepts a login.
- Version strings as the binaries report them, such as `0.9.8.8+a3c3e68` or `0.9.8.9-3+a3c3e68` are now compared correctly by the version check behind `GET /api/v1/cluster/activation`: build metadata after `+` is ignored and a trailing `-N` is a development build of that version. Before, a release build was read as a pre-release.
- `config.Save` and the console recovery command no longer follow a symbolic link planted at the temporary file name (`cluster.json.tmp`), and the file hand-over to the `dnshived` account no longer follows links.
- Groundwork for importing, copying, generating and restoring scopes (no screen uses it yet): a preflight check that compares a set of candidate scopes with the cluster and with each other and reports every clash as a structured finding with suggested fixes (another name, VLAN, VRRP ID, network or interface), and a remap that moves a scope to another network of the same size and lists every address it changed or left alone.
- The configuration content hash that the Overview, the catch-up and the start-up check compare did not cover six settings that a commit does distribute: `sanity_check_disabled` and the backup settings (enabled, interval, retention, password, replicate to peers). A node that differed only in those looked identical and was never repaired. A second hash (`config_hash_v2` in `/api/v1/status` and in the handshake) now covers them; the original hash keeps its value. The checks use the second hash when every node reports one and fall back to the original in a mixed-version cluster, so a rolling upgrade shows no false difference. A test fails if a new setting is pushed by a commit without being hashed.
- The users document now also carries a content hash in its revision stamp. Two different documents with the same revision are logged and written to the audit log as a conflict; one is still chosen deterministically, as before.
- The probe host now runs one DHCP probe runner and one DNS probe runner per physical interface that carries scopes (two worker interfaces plus a management interface give three of each), created and retired with the configuration. Before, one sequential queue per interface also ran the DNS queries, and every scope waited behind it: with 102 scopes on one interface a full pass took about 7.6 minutes, longer than the six minutes after which the Overview counts a result as stale, so the Overview kept reporting scopes as stale although every probe had succeeded.
- A DHCP probe moves on as soon as a lease is offered. It then listens a further 400 ms so that a second server answering at about the same time is still seen (dual-active detection), and a scope whose first answer is invalid or from more than one server is probed again over the full window to list every server. The wait is derived from the scope's last offer time (9 s for the first probe, then twice the last offer time plus 0.5 s, between 3.5 s and 9 s, because dnsmasq checks a new address by ping for about 3 s and handles one request at a time, so two probes that reach the same core together delay each other), and a scope that was not silent in the last cycle gets one retry over 10 s before a no-answer is published. Each result reports `offer_ms`, the time to the first offer. A `dhcp_wait_ms` set in `probe.json` still fixes the wait. DNS queries wait 2 s instead of 5 s.
- Each probe result now carries `dhcp_probed_at` and `dns_probed_at`, set when that part finished, and `dhcp_pending` / `dns_pending` while a part has not run yet. `probed_at` stays and is the newer of the two. A scope with only a DNS result shows it without waiting for DHCP, and the Overview judges staleness per part. A part that has not run yet is shown in orange as pending, in the grid, in the scope details and in the counts, which now use one rule: the number of pending scopes, the scopes swept and the coverage line agree. `parallel_probing` in `probe.json` and in `POST /api/v1/config` is still accepted and no longer changes anything.
- The management interface can serve scopes. Each interface in the cluster settings has a "use for serving" switch (`platform.serving` in `cluster.json`): worker interfaces serve unless switched off, the management interface serves only when switched on, which is the default off, so nothing changes on an existing installation. A scope on the management interface is untagged and uses the interface's existing static address, which dnshived never changes: no VLAN is built or removed there and the probe host uses a stable client MAC derived from the scope name, never the NIC's own, for its DHCP probe on it. An installation with one NIC can use it. An interface cannot be switched off while a scope is on it. A scope that already sits on the management interface keeps loading and stays selectable when it is edited. The interface order for the per-parent addressing keeps every worker's position and adds the management interface last. A probe host adopted after the switch is on gets `mgmt_interface` in `probe.json`; a probe host adopted earlier has to be adopted again or edited by hand to cover it.
- Manual probes. On the Probes page an operator can add a DHCP watch on any interface of the probe host, tagged or untagged, including the management interface when no scope is served there. The probe host sends a DISCOVER with a stable client MAC derived from the probe (a lease is never requested or taken, and the DHCP server re-offers one address instead of holding a new one for every probe) and lists every server that answers. Servers entered as expected are fine; any other server that answers is shown in red as a rogue, counted as a probe issue on the Overview and the Probes page, and written to the probe's event log when it appears and when it goes away. An empty expected list makes every answer a rogue. An interface that does not exist on the probe host shows an error, never "clear". A tagged manual probe builds its VLAN sub-interface without an address and removes it when the probe is removed, unless a scope uses that VLAN; the management interface is never tagged. The list is stored in the probe host's `probe.json` (`manual_probes`), changed through the probe's admin `POST /api/v1/config` and read with `GET /api/v1/watch`; it is applied live without a restart.
- The "Enable parallel probing" switch is gone from the Probes page: every interface now has its own runners. The explanation on the page was rewritten, and the probe host's state column shows "running".
- An interface can be switched off for serving once every scope on it is disabled. While an active scope is still on it, the change is refused, and the message gives the count and the first eight scope names. Disabled scopes stay where they are and keep loading. Enabling a scope on an interface that is switched off is refused the same way.
- New page Scopes, "Move all scopes from one interface to another" (`/scopes/move-all`). It moves every scope on the source interface to the target with VLAN ID, VIP, addresses and pool unchanged; nothing is renumbered. The check runs first and lists, per scope, every VLAN, subnet or address clash with the scopes that stay and with each other, plus the rule that the management interface takes untagged scopes only. The "stage" button appears only when there is no conflict, the staging checks again on the current configuration, and the move is a pending change that is reviewed and committed like any other. The move is always started by the operator; switching an interface off never moves a scope.
- Probes page: "prev", "next" and "refresh now" now keep the view on the results table. Before, every page change reloaded the page from the top, above the probe host settings, so the results had to be scrolled to again.
- Manual probes: the expected-servers list is merged into the table. Every DHCP server that answered is shown as a chip: green "known" (acknowledged), red "unknown", or grey "known, silent" for an acknowledged one that did not answer this time. "ack" on an unknown chip makes it known, "unack" undoes it; both are audited. A probe is added with name, interface and VLAN only. On an interface and VLAN where a scope is served, an unknown server cannot be acknowledged: a second DHCP server on a served segment stays a rogue. The stored form (`expected_servers`) and the API are unchanged.
- The probe API is meant to be HTTPS only. When a probe host is adopted it now reports its TLS certificate fingerprint, proven with the join code, and the web UI pins it at once, then closes the probe's plain HTTP port once the pinned TLS API answers (`plain_http` in `probe.json`, absent means on, so existing probes keep working). A probe adopted earlier shows "Pin now" on the Probes page: it displays the fingerprint it reports, to be compared with the probe's own log, and pins on confirmation; "Close plain HTTP" is offered once it is pinned. Closing is refused for an unpinned probe, and "Unpin" is not offered while the plain port is closed, so the web UI cannot cut itself off.
- A probe host's certificate can be replaced from the Probes page: paste a certificate and key (PEM). The key travels only over the pinned connection and an unpinned probe is refused. The probe checks that the key matches, that the certificate is neither expired nor not yet valid, an RSA key of at least 2048 bits and a chain of at most 8, swaps the files in as a whole directory so a failure keeps the old certificate, and serves the new one to new connections without a restart; the web UI pins the new fingerprint. dnshived-top and dnshived-validate need the new fingerprint (`-probe-pin`).
- Pinning a probe host from the Probes page ("Pin now", and the older "type the fingerprint" form) failed with "status 401 Unauthorized" on any probe that has API tokens, because the fingerprint was read from the token-protected status call over the unencrypted port. The probe now answers a public `GET /api/v1/tls-info` with only its TLS port and certificate fingerprint, and the web UI reads that; no token is sent over plain HTTP for it. A probe build without it is asked on the status call and, if that needs a token, the message says the probe has to be upgraded.
- Probes page: the small buttons ("probe now" after each scope, "ack" and "unack" on the manual probe chips) had grey text on the blue button and were hard to read; they now use a small-button style with the normal button text colour.
- Manual probes: next to each probe's chips there is an "add address" box to acknowledge a DHCP server that is not answering right now (a backup server, for example). It is not offered on an interface and VLAN where a scope is served, and a value that is not an IPv4 address is refused.
- Pinning a probe host failed at the last step with "TLS check with this fingerprint failed: TLS status 401 Unauthorized": the check asked the token-protected status call over the pinned connection. It now asks the public `tls-info` call, treats the pinned handshake as the proof (an answer of 401 passes), and also compares the fingerprint the probe reports over TLS with the pinned one.
- Pinning a probe host no longer asks the operator to compare a fingerprint when the probe can prove its certificate. The probe's public `tls-info` call, asked with a fresh nonce, returns a proof made with each of its admin tokens; the web UI holds one of them, recomputes the proof, and pins in one click. Right after pinning, the web UI replaces the probe's admin token over the pinned TLS connection (`POST /api/v1/rotate-token`, TLS only, the old token stops working at once), because that token was sent in cleartext while the probe was not pinned. A probe that cannot prove its certificate (an older build, or a different token) still gets the comparison dialog. The "type the fingerprint" form was removed from the Probes page. `dnshived-top` and `dnshived-validate` need the new admin token if they use it.
- The scope list can be sorted: click a column heading (Scope, Worker, Interface, VLAN, Subnet, Token Owner, Status, Pool, Probe). A second click reverses the order; the arrow sits in a fixed-width slot. Scope names sort naturally (scope-2 before scope-10), the interface column sorts by interface and then VLAN numerically, subnets by network address, and status, pool and probe put problems first. Ties always keep the scope-name order. The sort is part of the link, so paging, the auto-refresh and a bookmark keep it.
- Topology view: every interface is a collapsible section, collapsed by default. The heading shows the number of scopes and either "healthy" or how many need attention, so a collapsed interface never hides a problem. "expand all" and "collapse all" are links; the expanded set is kept in the address (`?open=ens19,ens20`) and follows each click, so a reload keeps it. The scopes inside an interface can be ordered by VLAN (default) or by name. An erroring scope named in the summary links to its interface opened.
- Scope list: the headings stay on one line and the scope name no longer breaks at the dash in a narrower window (the table scrolls sideways instead). Before, "Scope ▲" and "Token Owner" wrapped and the other headings were centred in the taller row.
- Scope list: the per-row buttons are replaced by one "☰" menu per scope: Open / edit, Disable or Enable, Rebalance to preferred core, Delete (in red, with the same confirmation as before). A click opens it; it closes on a click elsewhere, on Esc, when you choose an item, on scrolling, and once the pointer has been away for about 0.4 s (coming back cancels that). Only one menu is open at a time, it is placed from the button so the table cannot cut it off, and it opens upwards when there is no room below. Arrow keys move between the items. The rows are one line high again.
- Scope list: "Rebalance all scopes to their preferred core" is a small plain button on the right with a caution-coloured outline, its label says "(pending change)", and its tooltip says that it is not trivial and stages a pending change on every node.
- Probe details open in a popup, on the scope list and on the Probes page: "detail" shows the DHCP and DNS results of that scope, and "probe now" runs the check inside the popup (a note says it takes up to about 20 seconds) and shows the fresh result there. Without JavaScript both still open the full page, which is unchanged.
- Probe history. A probe host can keep what it finds: every result, or only failures, separately for DHCP and DNS (off by default, so nothing changes on upgrade). A failing scope's first success is written as a "recovered" line with how long it had been failing, in both modes. Manual probes follow the DHCP setting. Each record says when, which scope, interface and VLAN, the outcome with verdict and reason, the answering servers and first offer time (DHCP) or every check with the core it asked (DNS), and what the probe did to get it (retried, probed again over the full window, held back by the ownership debounce, started by hand). Records are written one JSON line each to `/var/lib/dnshived-probe/history` (mode 0600) and also to syslog with the tag `dnshived-probe-history` unless switched off. The files are capped, by default 4 files of 25 MB and 7 days, and the operator can change all three; a full write queue drops the oldest entries and counts them instead of slowing the probe down. Settings are on the Probes page ("Probe history") and apply at once, without a restart. The new page Probes, "Probe history" filters by scope, DHCP, DNS or manual probes, failures only and a time range (last hour to everything kept), pages back in time, and exports CSV (cells that look like a formula are defused). The probe details popup shows the last results of that scope. The probe answers `GET /api/v1/history` for it.

## 0.9.8.8 — released

- One password policy for web-UI passwords, `dnshived-web -reset-user` and `dnshived-web -hash-password`. A password needs at least 12 characters (an admin can change this between 8 and 64 on the Users page), an uppercase letter, a digit and a special character, at least five different characters, no simple sequence (`abcd`, `1234`, `qwer`), no block repeated over the whole password, and must not contain the user name, the local part of the mail address or the host name. The password forms show a strength bar with the unmet requirements in its tooltip, and the console tools print the same bar. Before, the only rule was a length of 10. Existing passwords keep working: a login with a password that does not meet the policy only logs a line. The strength is judged by length and variety; there is no check against lists of known passwords. **Upgrade note:** scripts that call `-hash-password` or `-reset-user -password` with a weaker password are now refused.
- The same policy applies to the backup password when it is set or changed in the web UI (backup settings, and a manual backup). A backup password that is already set keeps working. API tokens typed on the Security page must be at least 32 characters with at least 10 different characters, no whitespace and no simple sequence or repeated block (for example from `openssl rand -base64 32`); tokens that already exist are only checked when they are changed. The mail server password is not checked, because it belongs to the mail server.
- A user who logs in with a password that no longer meets the policy is taken to the change-password page first, with a notice and a link to continue without changing.

- The password-reset link in the mail is no longer built from the request's `Host` header. It uses the Public URL, else the management VIP on the web listener's port. With neither set, the "Forgot password" page says that reset by mail is off until an administrator sets one of them, and a request sends no mail and stores no token, with the same answer for every login name. Before, a request with a forged `Host` header could make the mailed link point at another host. **Upgrade note:** a cluster that has neither a Public URL nor a management VIP set loses reset by mail until one is set.
- The web UI's backup restore now counts wrong passwords. After 5 within 5 minutes from one user and client address, further restore attempts are refused for 30 seconds, doubling up to 15 minutes, before any decryption runs. Only a wrong password counts, not an unreachable node or an unreadable file. Restore decryptions run one at a time through their own slot, separate from the login slots, so a second restore waits for the first instead of failing, and a restore never times out. Before, anyone allowed to restore could try passwords without limit.
- A backup whose key-derivation count is 0 or above 1,200,000 is refused before any key is derived. dnshived writes 600,000.
- A stored web-UI password hash is only used if its sizes are inside the ranges dnshived could have written: a salt of 16 to 64 bytes, a key of 1 to 64 bytes and a PBKDF2 round count of 1 to 1,200,000 (dnshived writes 16 bytes, 32 bytes and 600,000). Any other hash is refused at login, with a log line naming the user, until the password is set again. The internal password-change endpoint that siblings on older versions use refuses such a hash with HTTP 400 and stores nothing. Before, a hash with billions of rounds in the users file or sent to that endpoint could hold a login for hours, and two of them made every other login wait and fail. **Upgrade note:** a stored hash outside these ranges stops working; the user sets the password again.
- Saving a scope no longer resets what the form does not show. Before, a plain save of the scope detail page cleared the scope's DHCP lease time, IoT defaults, disabled flag, `vrrp_unicast`, the links to its templates, its rebalance approval and the `dhcp_no_ping`, `dhcp_broadcast` and `dhcp_authoritative` options. The scope editor, which rewrites every scope, also dropped each scope's reservations, per-node address overrides and client DNS server. These fields are now kept from the stored scope. The probing checkbox of a disabled scope is read-only and keeps its stored value.
- `/api/v1/readiness/<scope>`: `config_validated` was always `false`, because it looked for a per-scope dnsmasq file that has not been written since DHCP and DNS moved to the central instances. It is now `true` when this node has rendered the DNS and DHCP configuration the scope needs, and `false` when the scope is missing from it (for example a DHCP range set without a gateway, which leaves the scope out of central DHCP). A scope with DHCP and DNS switched off has nothing to render and reports `true`. The response keeps all six fields.

- Preparation for later releases (nothing new is written yet). `cluster.json` and the scope definitions in it now keep keys this version does not know: they are read, carried through every edit, commit and candidate save, and written back unchanged. Before, a node on this version that saved the file would silently drop fields written by a newer version, which would have made a rolling upgrade lose data. The removed `dry_run` key is still dropped.
- `GET /api/v1/cluster/activation` reports whether every configured core member runs at least a given version (the version a later feature will need), and names the nodes that do not. Nothing depends on it yet; the arbiter and probe hosts do not count.
- A disabled scope now releases its VIP. Before, disabling a scope stopped its DHCP, DNS and probing but its VRRP instance kept running and the gateway VIP stayed up, so clients still reached a gateway that served nothing. The scope's keepalived instance is no longer rendered while it is disabled; the VLAN interface and the node addresses stay, and the scope's VRRP ID and VIP stay in the configuration (so the import and copy checks still count them). Enabling the scope brings the VIP back. **Upgrade note:** a scope that is already disabled loses its VIP on the first reconcile after the upgrade. The web UI texts that said "VLAN/VIP stay up" now say the VIP is released.
- The install and upgrade scripts now set `/etc/dnshived` to mode 0755. The relay, which runs as its own user, reads `relay.json` through that directory; a directory left at 0750 (for example by an earlier test install) made `dnshived-relay` fail with "permission denied" and restart every few seconds, and a package upgrade did not repair it.

## 0.9.8.7 — released

**Upgrade note:** upgrade every node in one window. The VRRP instances now authenticate their advertisements (see below), so a node on this release and a node on 0.9.8.6 cannot elect a VIP master together.

- VRRP advertisements are authenticated. Each scope's VRRP instance and the management VIP carry an `auth_type PASS` password derived from the cluster PSK with HKDF, so a host on the same segment can no longer take over a VIP by sending higher-priority advertisements. VRRP limits the password to eight characters; the derivation is per instance.
- keepalived runs with `CAP_DAC_READ_SEARCH` added to its capability set, so it can read the owner-only config (it can read files only, not write them).
- The rendered keepalived configs are written `0600` (they carry the VRRP passwords). The lease socket is `0600` instead of `0666`, so only the daemon's own user can send lease events.
- dnsmasq runs with `UMask=0077`, so the lease file (client MAC and IP records) is owner-only.
- The web UI caps each response it reads from a core node at 8 MiB.
- `dnshived-validate` writes its violation snapshots `0600`.
- The helper runs `restorecon` only when a dry run reports a file whose label is wrong, instead of relabelling on every start.
- VRRP advertisements stay multicast. The configuration accepts `vrrp_unicast` (cluster-wide under `scope_defaults`, or per scope) to send them unicast to the other cores' VLAN addresses; it is off unless set. A scope falls back to multicast if any core's address is missing, invalid or repeated.
- `scope_defaults.node_ip_suffixes` values must be a host number from 1 to 254.

## 0.9.8.6 — released

**Upgrade instructions (from 0.9.8.5):**

1. Back up `/etc/dnshived` and `/var/lib/dnshived` on every node, and `/var/lib/dnshived-probe` on each probe host.
2. Upgrade every node, including probe hosts, in one window. Do not upgrade one node at a time: a node on this release does not accept the unsigned pings and beacons of 0.9.8.5, and is isolated until the others follow. On Debian and Ubuntu install the new `.deb` with `apt-get install ./dnshived_<version>_<arch>.deb`; on RHEL-family systems use `rpm -Uvh dnshived-<version>.rpm`.
3. Wait until every node is `STABLE` (`journalctl -u dnshived | grep FSM:TRANSITION`) and the Overview in the web UI shows no unreachable node.
4. Probe hosts log their TLS certificate fingerprint at start (`journalctl -u dnshived-probe | grep 'TLS API'`). Pin it on the Probes page if you want the HTTPS path; unpinned probes keep working over plain HTTP.

**Changes to how commands run:**

- `dnshived-status`, `dnshived-validate`, `dnshived-preflight`, `dnshived-dnsrelay-render`, `dnshived-dhcp-probe`, `dnshived-relay --status`, `dnshived --version/--check-config/--emergency-close-gates` and `dnshived-web -reset-user` may run as root.
- The daemons and the DNS relay refuse root and must run as their service account; the unit files already do this.
- `dnshived-top` must not run as root.
- Unknown flags and stray arguments print one line and the usage and exit 2; `-h` lists the flags.

**Rollback:** install the 0.9.8.5 package on every node in one window (`apt-get install --allow-downgrades ./dnshived_0.9.8.5_<arch>.deb`, or `rpm -Uvh --oldpackage`), then restore the backups if the configuration was changed on this release. The 0.9.8.5 downgrade was exercised on the testlab.

- DHCP relay counts dropped packets per client VLAN, one counter per reason (gate closed, rate limited, malformed, and so on), and `dnshived-relay --status` prints them from the running relay. A full client table and a failed downstream write, which were not counted before, now are.
- The DHCP relay runs as its own system user and group, `dnshived-relay`, instead of `dnshived`, so a compromised relay cannot reach the privileged helper's socket. The daemon user joins the group to reach the relay's gate socket. The packages create both accounts, keep `relay.json` in the relay's group across upgrades, and restart a running relay. The unit also gains ProtectHome, ProtectKernelTunables, ProtectControlGroups, RestrictRealtime and LockPersonality. **Upgrade note:** upgrading restarts the DHCP relay on each node, which briefly interrupts DHCP relaying there.
- The relay's runtime directory `/run/dnshived-relay` is created by tmpfiles instead of the unit's `RuntimeDirectory=`, and an upgrade removes the old track files before the relay restarts. On SELinux-enforcing RHEL, the relay no longer fails to start after an upgrade with the old track files still present (systemd could not re-own them).

- Web UI search dropdowns (VLAN ID, VRRP ID and every other find-as-you-type list) showed only the first 200 entries with no sign that more existed, so the scope wizard's VLAN list ended at 201 and its VRRP list near 200. The list now ends with a "N more — type to narrow" row. Clicking into the field selects its text, so typing replaces the current value instead of appending to it, and an exact match is listed first, then values starting with the typed text, so Enter picks what was typed.
- `log_level` now takes effect; before, every level logged everything. `warning` logs errors, failures, denials and security refusals; `info` adds state changes (scope gained or lost, VRRP state, DHCP gate, failover, config commits, nodes joining or leaving, user changes); `debug` adds every routine repeating success (witness renewals, peer pings, probe results). `auto`, the default, logs like `info`, switches a subsystem (the part of a log tag before the colon, e.g. `AGENT` in `[AGENT:TOKEN_DENY]`) to `debug` detail for 5 minutes after a warning in it, and replaces the suppressed routine messages with one summary line every 10 minutes. Witness renewals no longer log a line every 5 seconds per scope. A level change applies without a restart. **Upgrade note:** a cluster set to `info` or `warning` now really logs less than before.
- Core nodes check every witness grant and renewal before counting it as an arbiter's vote: the PSK signature must be valid, the token must name this scope, this node and its current incarnation, and its expiry must be in the future and at most a minute ahead. Before, any `accepted` answer counted, so in a cluster without TLS a forged response could make a core serve a scope it did not hold. A rejected answer is logged with the arbiter's address and the reason. Arbiters have signed their grants since 0.5.2, so cores keep working with older arbiters during a rolling upgrade.
- DHCP relay: fuzz tests for the request and reply paths (malformed packets must never crash the relay or be forwarded with a wrong relay address) and benchmarks for per-packet cost, as the baseline for the relay hardening that follows.
- A scope could end up served by no node after its owner restarted: when a core that was serving a scope other than its preferred one restarted, it computed the preferred core as owner, while the other cores kept the restarted core as owner from their own last answer. With the same generation on all nodes, nothing noticed the difference and the scope stayed unserved until another restart or rebalance. A core now keeps a remembered owner only while that owner is seen serving the scope; once it has been seen not serving for 30 seconds, every core recomputes the owner the same way and they agree again. In a rolling upgrade, cores that are not yet upgraded behave as before.
- Upgrades restart a DHCP relay or DNS relay that still runs the old binary: when the daemon asks for a relay reload and the running process's binary has been replaced on disk, the helper restarts the relay instead and logs it. Before, an RPM upgrade only reloaded `dnshived-relay`, so it kept running the previous version until the next manual restart.
- A core rejoining the cluster takes over its peers' fencing watermark before it computes its first desired-state map, so that map carries the cluster's current generation instead of the node's older stored one.
- Cores compare their desired-state maps: each core announces a hash of its map (and the map itself for up to 512 scopes) in the peer handshake, and two cores with the same generation but different maps for more than 45 seconds (longer than the 30-second grace that heals the split after an owner restarts) log a `[DESIRED:SPLIT]` warning with the scopes they disagree on, every 5 minutes while it lasts and once when it ends; a shorter split of 5 seconds or more is logged with its length when it heals. Peers on older versions do not announce a map and are skipped.
- Faster recovery after a core that served a scope other than its preferred one restarts: when a peer's desired-state map disagrees at the same generation and this core's remembered owner is not serving the scope, the remembered owner is dropped right away instead of after the 30-second grace, so the cores agree on the next pass.
- `make rpm` packs new files that are not yet committed; before, the source tarball came from `git stash create`, which leaves untracked files out, so a build from a working tree with a new source file failed.
- A gap of 5 seconds or more in which no node served a scope is logged when a node serves it again (`[AGENT:UNSERVED] ... was served by no node for ...`), also below the 30-second warning, so every handover leaves its length in the log.
- DHCP relay limits, on by default: in-flight requests per VLAN are capped (`pending_per_vlan`, default 2048) and expire after 30 seconds instead of 120, so one flooding VLAN can no longer fill the relay's table for every other VLAN; each client MAC is limited per VLAN (`client_rate_limit`/`client_rate_burst`, default 10/s with a burst of 20) on top of the per-VLAN limit. A request dropped by any limit is counted and logged as a warning (at most once per 30 seconds per VLAN and limit). The new fields are optional in `relay.json`, kept when the file is re-rendered, and `-1` turns a limit off. The 1-minute relay metrics line gains `client_limited=` and `pending_full=` at its end. **Upgrade note:** a client sending more than 10 DHCP requests per second on one VLAN, or a VLAN with more than 2048 unanswered requests at once, now has requests dropped.
- Diagnosability: a scope that no node serves for more than 30 seconds is logged on every core as a warning (`[AGENT:UNSERVED]`) with that node's reason, the owner its desired-state map names and the generation, repeated every 5 minutes while it lasts, and once more when a node serves it again. Every change of a scope's owner in a node's desired-state map is logged (`[DESIRED:OWNER]`). Before, a scope that no node served produced no log line at all.
- Audit follow-ups: a `[DESIRED:SPLIT]` line lists at most 20 disagreeing scopes and then says how many more there are, instead of up to 512 scopes per line. The DHCP relay's per-client table holds at most 1024 MACs per VLAN and 16384 across all VLANs (before, 4096 per VLAN), and a flood of new MACs can trigger at most one idle-entry sweep per second. `make rpm` adds new files only under the source directories, not from the whole working tree.
- DHCP relay hardening. A reload that changed the DHCP server address could race with requests being forwarded at that moment; the server socket is now swapped atomically. An interface added in the same reload as a change of the cluster-wide `rate_limit`/`rate_burst` got the old values until the next reload; it now gets the new ones. Requests dropped by the rate limit cost less than forwarded ones (no log formatting while the warning is throttled), the clock is read once per request instead of twice, and replies are relayed without per-packet allocations in the common broadcast case. No configuration or behaviour change.
- The privileged helper's socket is hardened: each connection has a 60-second deadline and a 64 KiB request limit, at most 64 connections are served at once, and shutdown waits at most 45 seconds for requests in flight. Denied requests and the restart-helper and finish-decommission commands log the caller's uid and pid. The socket is created 0660 from the start, and a stale socket is removed only if it really is a socket; anything else at that path stops the helper with an error. Access is still decided by the socket's group, as before.
- Starting the daemon twice is refused: a second `dnshived` on the same node exits with an error naming the running process, before it binds any port or changes any service. Unknown command-line arguments now print the usage and exit with status 2; before, they were ignored and the daemon started. `--check-config`, `--emergency-close-gates` and `--version` are unchanged.
- The log line that reports a reload's effect on keepalived now reads `[AGENT:VRRP_PRIORITY] keepalived reloaded <N>ms after decision`, and the serving-set change line is `[AGENT:SERVING_SET]` (was `[BENCH:DECISION]`). Log text only; no behaviour change. Anything that greps for the old tags needs the new ones.
- The Makefile's `deploy` and `deploy-all` targets and their `VM_IPS`, `SSH_USER` and `SSH_OPTS` variables are removed. They copied bare binaries instead of installing a package and checked the result over plain HTTP against the HTTPS API, so they always reported the nodes as unreachable. Install the `.deb` or `.rpm` instead.
- Joining a core or adopting a probe no longer sends the cluster's secrets in cleartext. The push to a node in bootstrap mode (cluster config with the PSK and API tokens, web users, the web and cluster TLS keys, or the probe's config with its tokens) went over plain HTTP together with the join code, so anyone able to read the management network at that moment got all of it. The push is now encrypted and authenticated with a key derived from the join code (AES-256-GCM), and the join code itself is no longer sent. In bootstrap mode, the setup pages on port 80 now redirect to the HTTPS listener (port 443, self-signed), so join codes typed into the wizard are not sent in cleartext either; the machine API under `/api/` stays on port 80. If port 443 cannot be opened, the pages stay on plain HTTP as before. A node in bootstrap mode still accepts the old unencrypted push from an older sender and logs a warning that the secrets crossed the network in cleartext. **Upgrade note:** a node in bootstrap mode must run this version or later to be joined or adopted by it; an older one answers "wrong join code", and the error says to upgrade it first.
- The probe host verifies the cores it talks to. Before, it accepted any certificate, so a machine posing as a core could collect the probe's cluster token. Adopting a probe now also hands it the cores' certificate (the public part only, as `cluster_cert_pem` in `probe.json`), and the probe accepts only that certificate. A probe adopted by an older version has no `cluster_cert_pem` and connects as before, with a warning; adopt it again to get the check.
- "No cluster certificate configured — connections to cluster peers are not verified" is now logged as a warning, so it also shows at `log_level` `warning` and `auto`. Before, it was an info line and was hidden there.
- `dnshived-top` can verify the nodes against the cluster certificate: `-tls-cert <file>` (or `tls_cert=` in `~/.dnshived/rc`) with a copy of `/etc/dnshived/tls/cert.pem` from a core switches to HTTPS and accepts only that certificate, instead of `-tls-skip-verify`, which accepts any. The README quick start uses it.
- CI runs the tests: `go test ./...` (as root with a `dnshived` service user, as on a real install), the race detector on the coordination and safety packages, and a build of every binary including the DNS relay module, which it did not build before. Before, CI only built and vetted.
- The quorum calculation has its own tests, including every possible split of the three cores: two nodes that cannot see each other never both hold quorum.
- README: the safety promise now names the conditions it rests on and the clock assumption, instead of calling the failure mode structurally impossible.
- An arbiter that restarts grants no new witness tokens for 15 seconds (one token lifetime). Grants were written to disk up to 2 seconds after they were answered, so an arbiter that crashed right after a grant could forget it and grant the same scope to a second core while the first core's token was still valid. During the pause, renewals keep working and the arbiter re-learns any grant it lost from the holder's signed renewal; anything it does not re-learn has expired by the end of the pause. A request refused this way is answered as a normal denial with the remaining time. A restarted core still gets its tokens from the other two arbiters.
- A corrupt or unreadable `incarnation` file no longer resets the node's incarnation to 1, which could repeat a value the node had already used. The node now takes the current Unix time as its incarnation, which is higher than any value the counter reached before, and logs a warning naming the file.
- A daemon started as root on a node that has the `dnshived` service user is refused with an error naming that user; before, a root run rewrote the dnsmasq and keepalived configuration files as `root:root`, and dnsmasq, which runs as `dnshived`, failed with "Permission denied" until the real daemon rewrote them. Configuration files written while running as root are now owned by `dnshived:dnshived`, and a leftover temporary file from an earlier run no longer blocks the next write. `--version`, `--check-config` and `--emergency-close-gates` still work as root; bootstrap mode is unchanged. **Upgrade note:** a custom unit that runs the daemon as root no longer starts; the shipped unit has always used `User=dnshived`.
- The web UI's Basic-auth verify cache is keyed by HMAC-SHA256 under a random secret that exists only in the process, instead of an unkeyed SHA-256 of the username and password. A memory dump of the web UI no longer gives an offline guessing target for passwords. The cache is in memory only, so nothing changes on disk and a restart just empties it.
- A daemon start no longer knocks the scope VIP off the node. The daemon now sends the VIP with each interface request, and the helper removes only addresses that match neither the node IP nor the VIP. Before, every start deleted keepalived's VIP, and it came back about 0.6 s later, so the holder flapped MASTER → BACKUP → MASTER. An older helper with a newer daemon behaves as before.
- A probe host can be adopted again after a core node self-decommissions. Adopting a node as a core stops its probe units so the two roles never run together; a self-decommission now starts them again before the node returns to bootstrap mode.
- A self-decommission removes the empty `inet dnshived` nftables table that older versions left behind.
- When no scope is eligible for the relay, `relay.json` no longer keeps the client interfaces of removed or disabled scopes: the file is emptied (rate limits kept) before the relay is stopped.
- A scope can be moved to another VLAN ID or trunk interface from its page. Only the parent and VLAN ID change; the VIP, node IPs and DHCP pool stay as they are. The move is staged like any other edit, and a VLAN already in use on that trunk is refused.
- Probe hosts serve their API over HTTPS on port 9445 with their own self-signed certificate, separate from the cluster's. Its SHA-256 fingerprint is logged at start and shown on the Probes page. The web UI and `dnshived-top` (`-probe-pin host:port=sha256:…`) can pin that fingerprint, and a pinned probe is then reached only over HTTPS with that certificate. The web UI checks the probe over TLS before it saves a pin. The plain API on port 9444 stays until every probe is upgraded; probes not yet pinned keep working over plain HTTP and are shown as such. A probe's certificate is regenerated after a self-decommission, so its pin must be set again.
- `dnshived-validate` reaches pinned probes over HTTPS too (`-probe-pin host:port=sha256:…`, or the pins in `web.json`), and the Probes page can remove a pin (Unpin), which returns that probe to plain HTTP until it is pinned again.
- A failed relay close no longer releases the scope's arbiter token. The token is kept and renewed until the relay confirms the close, and the close is retried each tick (`[AGENT:CLOSE_PENDING]`, then `[AGENT:CLOSE_RESOLVED]`). Before, a refused close cleared the token, so another core could open the scope while this relay still forwarded DHCP for it.
- An open whose answer from the relay was lost is closed on the relay before its token is dropped, so the relay cannot keep forwarding without a token.
- The probe helper's trunk-parent allowlist no longer accepts VLAN-style names or the interface that carries the default route, and its interface reconcile no longer removes IPv6 (link-local included) addresses.
- **Upgrade note:** upgrade all cluster nodes in one window. A node running this release does not accept the unsigned pings and topology beacons of 0.9.8.5 (they are refused as `DENY_UNSIGNED`), so during a rolling upgrade the upgraded node is isolated from the others until they are upgraded too.
- An upgrade from 0.9.8.5 removes the nftables DHCP rules that release left behind. The removal ran before the helper was connected, so it failed silently and the rules kept dropping DHCP on the nodes that owned a scope. It now runs after the helper is connected.
- Files the daemon and helpers write for dnshived (`dnsmasq` host files, the DNS relay and probe configs, the web users file) are owned by `dnshived:dnshived` even when root writes them.
- Every binary checks its command line: an unknown flag or a stray argument prints one line and the usage, and exits 2; `-h` lists the flags.
- Every binary checks the user it runs as. The daemons (`dnshived`, `dnshived-relay`, the DNS relay, the probe and the web UI) refuse root and need their service account, and a missing account is an error. The root helpers need root. The tools that can need root (`dnshived-status`, `dnshived-validate`, `dnshived-preflight`, `dnshived-dnsrelay-render`, `dnshived-dhcp-probe`, and the root-capable modes of `dnshived --version/--check-config/--emergency-close-gates`, `dnshived-relay --status` and `dnshived-web -reset-user`) may run as root. `dnshived-top` refuses root.
- A second copy of a daemon or helper refuses to start and names the running process. Each keeps a lock file, and a socket path is replaced only when nothing answers on it; a socket that still accepts connections is refused.

Hardening and fresh-install release. dnshived runs unprivileged, with root left only in the helpers and keepalived; RHEL/CentOS (SELinux) install and upgrade paths fixed; web UI security hardening and performance; founding wizard stores node addresses with their port, so a freshly founded cluster no longer comes up partitioned. Measured on a lab core before: ~107 process starts and 4.2 s CPU per minute.

- dnshived-web-helper and dnshived-probe-helper no longer reset /run/dnshived to 755 on start (that undid the sticky group-writable mode, so dnshived could not recreate its lease socket after a web-helper start).
- dnshived-relay and dnshived-probe drop CAP_NET_RAW: binding a socket to an interface needs no capability since Linux 5.7, and every supported OS has 5.14 or newer.
- dnshived-web-helper keeps root but no capabilities at all (its only command is restarting dnshived-web), plus NoNewPrivileges and a read-only system.
- keepalived and dnsmasq units no longer set NoNewPrivileges: under SELinux it blocks their transition into keepalived_t/dnsmasq_t, so keepalived could not open VRRP sockets and dnsmasq did not start (found on CentOS Stream 9). Their capability limits stay.
- The pre-onboarding interface match never detected any trunk on a running cluster: its listener used UDP 9446, which the topology beacons already hold on every trunk, and the bind error was swallowed. Interface probes now use UDP 9448, and a failed listen is logged.
- Replace/onboard is refused (HTTP 409, nothing changed) when the interface check hears no candidate interface on a trunk; the web UI's Pending changes page offers an explicit "onboard anyway" checkbox for the commit.
- RPM binaries report the same version string as the .deb (VERSION-N+HASH); the different format made the pre-onboarding check report a version mismatch between identical builds.
- Onboard and replace store the node's real interface names: the pre-onboarding interface match (the candidate's broadcast bursts heard on the cluster's trunks) is saved per node, as founding already did; a replace drops the old node's entries. The management interface gets a per-node name too, taken from the interface the cluster reaches the candidate on.
- relay.json was written with the cluster's interface names even on a node whose names differ (the change check used the resolved names), so the relay could bind the wrong interfaces.
- RPM/SELinux: the lease file and dnsmasq log in /var/lib/dnshived get dnsmasq_lease_t/dnsmasq_var_log_t; dnsmasq_t could not write them (var_lib_t), so central DHCP could not start on RHEL-family.
- A scope VLAN that already exists under another name (same VLAN ID on the same NIC, e.g. ens19.110 after the node's names resolve to eth1) is removed and recreated under the right name instead of failing with "VLAN device already exists".
- Every node resolves configured interface names to the kernel name (a kernel altname such as ens19 on a host booted with net.ifnames=0 now maps to eth1) before using them for keepalived, beacons, rp_filter and sockets; before, `ip` accepted the altname while the rest failed.
- Self-decommission and the orphan sweep could not delete VLAN interfaces on a node whose interface names differ from the cluster's: they passed the cluster's trunk name to the helper, which then deleted a non-existent ens19.110 instead of eth1.110 and reported success.
- Self-decommission empties /var/lib/dnshived instead of failing to delete the directory itself (the non-root daemon may not remove it), and no longer asks the helper to stop the dnsmasq@ template unit.
- RPM upgrade restarts only running units: it never restarted a running web UI (it kept serving the old binary) and started the probe pair on core nodes.
- RPM: the post-install script called /usr/bin/dnshived-preflight, but the package installs to /usr/local/bin. The script aborted there, so an RPM install never set the SELinux file contexts or enabled/started any service, while dnf still reported success.
- dnshived-probe-helper and dnshived-probe-vlans@ keep root only with the capabilities they use, plus NoNewPrivileges.

## 0.9.8.1 — released
Bugfix release for the pulled 0.9.8, from a fresh 4-VM Debian 13 install and repeated fresh-cluster runs.

**Upgrade note: dry-run is gone. A cluster that is in dry-run today starts serving real DHCP/DNS as soon as this release is installed.**

Install and packaging
- New `dnshived-preflight` runs at install time: checks required binaries and stops/masks the distro's own `dnsmasq.service`, which wildcard-binds port 53. A failed check aborts the install with a clear message. Only a wildcard bind on 53 is flagged, not dnshived's own listeners.
- `dnshived-probe` and `dnshived-probe-helper` run as the `dnshived` account (they hardcoded a non-existent `admin` user); `probe.json` is group-readable by `dnshived`.
- docs/INSTALL.md recommends `dnsmasq-base`, not `dnsmasq`.
- `dnshived-web` and `dnshived-web-helper` keep running across a package upgrade.
- Probe, probe-helper and per-scope dnsmasq units have a restart limit (10 in 5 minutes).
- One join code per fresh host, valid for either role, in `/run/dnshived-bootstrap/otp` (no longer in /tmp).
- `dnshived-web -reset-user` leaves `webui-users.json` readable by the web UI (0640, group `dnshived`).

Founding and onboarding
- A founded cluster enables privilege separation by default (`helper_socket` set); the field is no longer editable in the web UI.
- Founding derives the probe host's TLS setting from the core config, so a probe adopted at founding can fetch its configuration.
- Founding fills the probe's `trunk_parents`, and the probe helper reads them from `probe.json` live.
- New /24 scopes get suggested defaults: VIP .254, gateway .1, DHCP pool .200-.250, upstream 1.1.1.1 and 8.8.8.8. Other prefix lengths are left to the operator.
- Onboarding no longer restarts dnshived on the existing cores, keeps a configured member that is currently down, and no longer shows healthy peers as UNREACHABLE right after a start.
- A bare address without a port gets the convention port (daemon and web forms).
- An unreachable node can be force-removed from membership, behind a second confirmation.

Decommission
- A decommissioned node no longer stays "alive" on the survivors (backup-path results and trust scores cleared).
- A decommission reaches every surviving node, and re-onboarding at an old address re-adds the peer everywhere. Overview warns when nodes disagree on membership.

Network plane
- VLAN construction brings the parent trunk up first (helper, probe helper and direct mode).
- `rp_filter=0` on trunk parents (the units may write `/proc/sys/net/ipv4/conf`), so Debian 13 nodes see topology beacons on their trunks; a TRUNK PATH coherence warning names the likely cause.
- Topology beacons start on trunks added at runtime, without a restart.
- Core nodes agree on a scope's owner after a restart (observed lease holder, not own history).
- Probe coverage for untagged scopes (vlan_id 0).

DHCP and DNS
- dry-run removed: every node always serves; a legacy `dry_run` key is stripped on load (docs/FREEZE.md updated, contract break).
- Central DHCP renders option 54 (the scope VIP) and option 6 (every configured core's address) explicitly, and the relay keeps option 54 at the VIP, so renewals survive a failover.
- The probe accepts the scope VIP as a legitimate DHCP server: no false ROGUE DHCP.
- The dead per-scope `upstream` field is removed everywhere; the cluster-wide upstream stays.
- VIP, gateway, node_ip and DHCP range may not be a subnet's network or broadcast address.

Web UI
- Saving a change no longer drops the management VIP: keepalived-mgmt is reloaded only when its config changed, and a VIP change moves the address without a fresh election. `vip_host` follows the VIP live, and the Saving page finds the UI at the new VIP.
- Ports 80/443 redirect to the web UI (`CAP_NET_BIND_SERVICE` only, never root).
- The wizard no longer suggests the network address as VIP.
- Inline "probe now" button on the Probes tab.
- Cluster paths lists VLAN paths under their trunk, collapsed, with an unreachable count.

## 0.9.8 — released
